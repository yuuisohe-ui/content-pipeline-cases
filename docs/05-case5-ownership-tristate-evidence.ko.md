## 5. 핵심 전환점

### 5.1 전환점 1: 읽기 전용 잠금이 아닌 fork — 예상과 다른 과정의 사실 기록

**예상 서사**: “AI가 처음에는 읽기 전용 잠금 방안을 기본값으로 제시했고, 본 연구자가 fork로 변경하도록 요구했다.”
**검증 결론**: **성립하지 않는다**. 실제 과정은 다음과 같다.

1. `<V-msg#1358>`의 사용자 원문은 **편집 동작을 지정하지 않았고**, “비관리자의 삭제·추가·수정은 자신의 계정에만 적용된다”고만 설명했다.
2. `<V-msg#1359>`(AI, 05-10 13:09)는 먼저 방안을 제시하지 않고 확인할 질문 네 가지를 제시했다. 이 가운데 “수정 동작” 항목에는 **세 가지 선택지가 병렬로 제시되었다**.
   - 개인 복사본 생성(포크)
   - 수정 자체를 금지(읽기 전용 잠금)
   - 공용 숨김 + 새 개인 항목
3. `<V-msg#1360>`에서 사용자는 그중 **`개인 복사본 생성 (포크)`**를 선택했고, 동시에 “삭제 동작”에서는 `본인 화면에서만 숨김`을 선택했다(이 역시 양자택일 항목 중 하나였다).

따라서 정확한 서술은 **AI가 설계 공간을 선택지로 펼치고 사용자가 선택했다**는 것이며, “AI가 잘못된 방안을 내고 사용자가 수정했다”는 것이 아니다. 이는 여전히 실제적인 인간 판단이다. 사용자는 “더 간단한 읽기 전용”과 “더 복잡한 포크” 사이에서 후자를 선택했다. 다만 이는 **선택형 판단**이지 **거부형 판단**이므로, 사례 1~4에서 반복적으로 나타난 “AI가 먼저 구현하고 사용자가 뒤집는” 양상과 다르다.

**이 선택은 수업 현장에서 비롯되었는가?** `<X>`. `#1358`–`#1362`의 사용자 메시지 네 건에는 fork를 선택한 이유를 설명하는 **수업·교사·학생 사용 상황에 대한 언급이 전혀 없다**. 사용자가 제시한 유일한 추가 이유는 `<V-msg#1360>`의 개인정보 보호 관련 진술, 즉 “他登陆之后他账号下的内容别人都不能看到，具有隐私性。”이다. 현재 자료로는 fork를 수업 요구에서 비롯된 것으로 귀인할 수 없다. 자료가 뒷받침하는 귀인은 **개인정보 격리 + 편집 가능한 경험 유지**이다.

### 5.2 전환점 2(더 강함): `#1398`이 `본인 화면에서만 숨김`을 뒤집음

실제로 “사용자가 AI 구현을 뒤집은” 사건은 사흘 후 발생했다. 더구나 사용자가 `#1360`에서 직접 선택했던 방안을 뒤집은 것이었다.

- `#1360`에서 사용자가 선택: 공용 항목 삭제 = 본인 화면에서 숨김 → `hidePublicItem()`으로 구현.
- `#1398`에서 사용자가 해당 경험을 부정: **“显示什么목록에 숨겼다 不要这样，直接丢到垃圾桶里”**. 아울러 전체 수치가 변하지 않는 문제도 지적했다(“整体的数字不变”).
- 결과: `move_to_trash(_table, _id)` RPC가 만들어졌다(`20260514145854`가 HEAD 버전). 로직은 “비관리자가 공용 항목 삭제 → 먼저 `fork_public_item`으로 개인 복사본 생성 → 해당 복사본의 `deleted_at := now()`”로 바뀌었다.

**이것이 본 사례에서 가장 가치 있는 판단이다.** 사용자는 기술적으로 더 단순하고 의미론적으로도 일관된 방안(숨김)을 **사용자가 인지하는 일관성**을 이유로 거부했다. 즉, 삭제 후에는 복구 가능한 휴지통이 있어야 하고 수치도 변해야 한다는 것이다. 이 순수한 경험 계층의 요구를 충족하기 위해 시스템은 한 번의 삭제를 후면에서 “깊은 복사 + 소프트 삭제”의 두 단계 쓰기로 처리하는 비용을 감수했다.

**직접적 결과(검증 가능)**: 이후 `hidePublicItem()`은 프런트엔드에서 **호출자가 전혀 없는 함수**가 되었다(HEAD 대조: 0개). 그러나 `hidden_public_items` 테이블 자체는 여전히 작동한다. `fork_public_item` 내부에서 원본 공용 항목을 숨기기 위해 이 테이블에 기록하고 `<C-supabase/migrations/20260510131848...sql>`, `fetchHiddenIds`는 여전히 7곳에서 이를 읽기 때문이다. **즉, 프런트엔드의 “쓰기” 경로는 제거되었지만 “읽기” 경로는 유지되었고, 쓰기 책임은 데이터베이스 함수 내부로 내려갔다.**

### 5.3 전환점 3: 50곳의 insert 수정을 트리거로 대체

`<V-msg#1363>`(AI, 05-10 13:25)은 “50개 파일을 모두 수정하지 않고도 동작하도록, DB 트리거로 `owner_id`를 자동 설정합니다.”라고 설명했다.
이는 사용자가 요구하지 않은 AI의 자율적인 공학적 판단이었다. 그 대가는 단계 B에서 나타났다. service role을 사용하는 모든 edge function에서는 `auth.uid()`가 null이므로 이 트리거가 작동하지 않았고, `#1372`와 `#1376`의 “왜 여전히 공용으로 표시되는가”라는 두 차례 재작업으로 이어졌다. 결국 `analyze-song`과 `generate-lesson-plan` 모두 `owner_id`를 직접 기록해야 했다.

### 7.2 따라서 내릴 수 있는 정확한 성격 판단

- 이는 **up-front(전면적) 추상화**이다. AI가 동일 세션(`#1363`)에서 공유 모듈을 먼저 작성한 뒤 각 페이지에 연결했으며, 4개 페이지 모두 4분 이내에 연결되었다.
- 본 프로젝트에서 **실제로 여러 모듈이 공유하는 유일한 비즈니스 로직 모듈**이라는 점은 사실이다(비교: 사례 1의 타임라인 로직은 `lines.ts`와 두 edge function에 분산되어 각각 구현되었고, 사례 4의 자막 폴백 체인은 여러 곳에 복제되었다). **“진정한 재사용이 이루어졌다”는 판단은 성립하지만**, 그 이유는 “리팩터링을 거쳐 추출했기 때문”이 아니라 “최초부터 공유 모듈로 작성했기 때문”이다.
- 재사용의 **확산**은 점진적이었다. 2026-05-10에는 호출 파일이 4개였고, 2026-06-07에는 8개, 2026-07-01에는 9개로 늘었다. 또한 단계 D의 확산은 사용자가 “数据逻辑全部保留不动，只改UI层”(`<V-msg#1708>`)이라고 명시한 상황에서 AI가 신규 컴포넌트에 기존 모듈을 자율적으로 이어 쓴 결과이다. **이는 “모듈이 계속 사용되었다”는 증거이지 “사용자가 재사용을 추진했다”는 증거는 아니다.**

### 7.3 불완전한 재사용의 세 가지 측면(사실대로 기록)

1. **내보낸 기호 7개 중 4개가 죽은 코드**이다(`applyHiddenFilter`, `hidePublicItem`, `isPersonal`, `isPublic`). 이 중 `hidePublicItem`은 `#1398`의 제품 결정으로 도태되었으며, `isPersonal`/`isPublic`은 **처음부터 사용된 적이 없다**. 각 컴포넌트는 오히려 `owner_id ? "개인" : "공용"`을 인라인으로 작성했다. 예: `<C-src/components/lessons/SortableLessonPlanCard.tsx:159>`, `<C-src/pages/Courses.tsx:130>`의 `!course.owner_id && !isAdmin && user`. 즉, **공유된 것은 “동작”(fetch/fork)이고 “판정”(누가 누구에게 속하는가)은 공유되지 않았다**. 판정 로직은 9개 파일에서 제각기 작성되었다.
2. **`CreateCourseDialog.tsx:136`은 모듈을 우회해 RPC에 직접 연결된다.** 이는 제약이 메커니즘이 아니라 관행에 의존한다는 의미이다(`ownership.ts`가 유일한 진입점으로 강제되지 않았으며 `fork_public_item` RPC는 모든 클라이언트 코드에 열려 있다).
3. **`Materials.tsx`는 완전히 다른 모델을 사용한다.** `<C-src/pages/Materials.tsx:157>`은 `is_public.eq.true,user_id.eq.${user.id},is_shared.eq.true`라는 세 조건의 or 쿼리를 사용한다. `materials` 테이블에는 `owner_id`도 `set_owner_trg`도 없다(트리거 목록 대조로 확인). 이후의 `courses.is_public`(2026-06-09, `#1760`)은 세 번째 공개 의미론을 도입했다. **따라서 HEAD의 플랫폼에는 세 가지 콘텐츠 가시성 모델**(`owner_id IS NULL` / `is_public` 불리언 열 / `materials`의 삼상태 or 쿼리)이 동시에 존재한다. 본 메커니즘은 그중 가장 큰 체계(13개 테이블)를 포괄하지만 플랫폼 전체를 통일하지는 못했다.

## 8. 본 사례에서 논문에 수록할 수 있는 결론(자료가 뒷받침하는 부분만 서술)

1. **설계 공간은 AI가 펼치고, 인간이 선택했다.** `#1359`의 네 가지 질문과 세 가지 선택지는 AI가 자율적으로 생성했고, 사용자는 4분 이내에 네 항목을 모두 선택했다(`#1360`). 이와 같은 “AI가 선택지를 제시하고 인간이 판단하는” 협업 방식은 본 프로젝트에서 “AI가 방안을 내고 인간이 교정하는” 방식보다 효율적이었다. R1–R3은 17분 만에 13개 테이블에 걸친 권한 모델을 산출했다.
2. **기술적으로 자족적인 방안도 경험 계층에서는 실패할 수 있다.** “본인 화면에서 숨김”은 RLS와 데이터 일관성 측면에서 결함이 없었으나, toast 문구와 수치 미갱신 때문에 사용자에게 거부되었다(`#1398`). 그 결과 시스템은 한 번의 삭제를 “깊은 복사 + 소프트 삭제”로 바꾸어야 했다. **방안의 수용 가능성을 판단하는 기준은 구현의 간결성이 아니라 사용자의 경험에서 나온다.** 이는 앞선 네 사례에서는 나타나지 않은 유형이다.
3. **전면적 추상화는 재사용을 낳지만 일관성을 보장하지는 않는다.** `ownership.ts`는 3개월간 한 번도 수정되지 않았고, 9개 파일의 15개 지점에서 호출되었다. 이는 전면적 추상화가 여기서는 효과가 있었음을 보여준다. 그러나 내보낸 기호 중 4/7가 죽은 코드이고, 한 곳이 모듈을 우회하며, 플랫폼 내에 세 가지 가시성 모델이 병존한다는 사실은 **공유 모듈 자체가 제약으로 기능하지 않음**을 보여준다. 논문에서 “AI 협업 아래의 아키텍처 일관성”을 논하려면 이 긍정적·부정적 데이터를 함께 제시하는 것이 적절하다.
4. **트리거 방식 전환의 이익과 비용은 정량화할 수 있다.** 이익은 약 50개 파일의 insert 수정을 피한 것이며(`#1363`), 비용은 service-role 경로의 실패로 R4와 R5에서 총 10회 커밋의 재작업이 발생한 것이다.
