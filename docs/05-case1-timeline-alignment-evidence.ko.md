> ⚠️ 修正一个关于 Suno 时间戳的严重误解
>
> 你之前以为 Suno API 的 alignedWords 是"按字返回，需要按 0.6s 间隔分组成行"——这是错的。
>
> 实际上 Suno 的 /api/v1/generate/get-timestamped-lyrics 接口返回的 data.alignedWords 数组里，**每一项 (item.word) 就是完整的一行歌词**，并且行末自带 "\n"（段落分隔处是 "\n\n"）。比如真实样本：
>
> ```
>   { "word": "朋友的路途多漫长\n",   "start_s": 19.388, "end_s": 24.335, "p_align": 0.95 }
>   { "word": "携手并肩共欣赏\n",     "start_s": 24.454, "end_s": 26.848, "p_align": 0.95 }
>   { "word": "心中梦想共徜徉\n\n",   "start_s": 34.069, "end_s": 38.537, "p_align": 0.95 }
> ```
>
> 所以请按下面的方式重写歌词时间戳逻辑：
>
> 1. 把 Suno 返回的 alignedWords 直接当成"按行对齐"的数据源，不要再做任何 0.6s gap 分组：
>
> ```
>    type SunoLine = { text: string; startS: number; endS: number };
>
>    function parseSunoLines(alignedWords: Array<{word:string; start_s:number; end_s:number}>): SunoLine[] {
>      return alignedWords
>        .map(w => ({
>          text: w.word.replace(/\n+$/g, "").trim(),   // 去掉行末 \n
>          startS: w.start_s,
>          endS:   w.end_s,
>        }))
>        .filter(l => l.text.length > 0);              // 过滤掉空行（段落分隔产生的）
>    }
> ```
>
> 2. AI 生成的 lyrics（analysis.lyrics_with_pinyin）和 Suno 的 sunoLines 行数仍可能不一致（AI 偶尔多写/少写、Suno 偶尔合并重复句）。解决：
>    做一次"按顺序对齐"——以 sunoLines 为时间真值，把 lyrics 数组按顺序 zip 上去；多出来的 lyrics 行复用上一行 startS，多出来的 sunoLines 直接丢弃。代码：
>
> ```
>    function alignLyricsToSuno(lyrics: LyricLine[], sunoLines: SunoLine[]) {
>      return lyrics.map((line, i) => {
>        const s = sunoLines[Math.min(i, sunoLines.length - 1)];
>        return { ...line, startS: s.startS, endS: s.endS };
>      });
>    }
> ```
>
>    ❗ 不要再用 "lineStarts[i] = alignedLines[round(i * alignedLines.length / lyrics.length)].startS" 这种比例映射，会让中间几行时间戳错位 5–10 秒。按顺序 1:1 + 末尾 clamp 才是正确做法。
>
> 3. 点击跳转和高亮都直接用 alignLyricsToSuno 返回的数组里的 startS / endS：
>    - 点击第 i 行：audio.currentTime = aligned[i].startS
>    - 高亮：用 requestAnimationFrame 读 audio.currentTime，二分查找满足 startS <= t < (下一行 startS) 的 index
>    - 弹幕 / stageOverlay 也用同一个 currentActiveIndex，不要再判断 hasTime
>
> 4. 不要去问 Suno "只返回每行第一个字"——它本来返回的就是行级的，没有更细的字级 API。如果将来想做卡拉OK 逐字高亮，需要前端按行内字符数 + (endS - startS) 线性插值，目前不需要。

**전환점 A · #1464(05-18 18:41) — 도메인 관찰로 AI의 데이터 모델 가정을 뒤집다**

1. AI의 오류를 "구현 세부"에서 "데이터 모델" 층위로 끌어올렸다. 이전 두 번의 수정(`23f8f74d`–`d9bbff77`)은 실질적으로 잘못된 가정 위의 땜질이었다.

**전환점 B · #1472(05-19 05:09) — 교육적 일관성 요구가 수정 위치를 프런트에서 백엔드로 밀어 올리다**

#1464 이후 프런트는 이미 "보기에는 정렬된" 상태였다. 그러나 #1472의 세 번째 항목 — "suno演唱的音乐歌词和出现在音乐卡片的教学歌词完全对应上" — 은 결함 보고가 아니라 **제품/교육 층위의 등가성 요구**였다. 그 결과 해법이 "프런트의 clamp 폴백"에서 "백엔드의 행 수 불변식 보장 + 기존 데이터 일괄 복구"로 바뀌었고, `sg-repair-aligned`(`80532fe4`)와 `analyze-generated-song`의 `expected_line_count` 계약(`sg-repair-aligned` L120)이 직접 파생되었다. **프런트의 clamp는 같은 라운드에서 삭제되었다**(`e3c9f52c`: 잘못된 타임스탬프를 재사용하느니 `-1`을 기록해 UI의 클릭을 비활성화하는 편을 택함). 이는 "없느니만 못한 오류는 피한다"는 취사선택이며, 그 판단 기준은 코드 논리가 아니라 교육 현장의 요구에서 왔다.

**전환점 C · #1468과 #1472, 두 차례의 "진단만 하고 코드는 고치지 말라"는 지시**

두 메시지 모두 "코드를 수정하지 말라"고 명시했다. 그 효과로 #1469와 #1473은 본 사례에서 유일하게 **실측 데이터를 갖춘 근본 원인 보고서** 두 건을 산출했고, 이는 제7절에서 활용 가능한 유일한 "수정 전 상태" 증거이기도 하다. 이 상호작용 방식 자체가 이전 가능한 방법론적 소재다.

## 6. 수정 전 / 후 효과의 입증: 검증 가능한 부분과 불가능한 부분

### 6.1 검증 가능한 "수정 전 상태"(모두 대화 아카이브 내의 데이터베이스 실측 출력)

| 증거 | 위치 | 내용 |
| --- | --- | --- |
| 필드명 불일치로 타임스탬프가 전부 0 | **#1469, 2026-05-18 18:52** | 「未来的歌」 `id=b9e5415b-4d98-4d09-ad6c-4f9a9498bcf0`. `aligned_words`는 non-null, array, 길이 27. 앞 3건의 실제 값은 `{"word":"每一天都是新的开始，\n","startS":9.096,"endS":14.0025,"pAlign":0}` 등. `parseSunoLines`는 `start_s/start`를 읽어 전부 0으로 폴백. 이로부터 `currentActiveIndex`가 항상 `aligned.length - 1`과 같아진다는 결론 도출(현상: "하이라이트가 늘 마지막 행에 있고 어느 행을 눌러도 0초로 seek") |

이 두 지점이 본 사례의 "수정 전 효과"에 대한 가장 강한 증거다. 사후 서술이 아니라 **당시 운영 데이터베이스에 대한 실제 질의 결과**이기 때문이다. 대조 방법: 대화 아카이브 #1469와 #1473의 전문을 열람.

### 6.2 검증 가능한 "수정 후 상태"

- **코드 층위 검증 가능**: `lines.ts` L80–81의 `-1` 센티널, `sg-repair-aligned` L120의 `expected_line_count`, L98–101의 멱등 병합은 모두 HEAD `74c64e66`에서 직접 확인할 수 있다.
- **동작 층위 서술**: #1475(05-19 05:15) 말미의 완료 진술 — "새로 생성된 곡은 `sg-finalize-song`에서 행 단위 타임스탬프를 병합 → GPT에 행 단위 엄수 번역을 시킴 → 프런트는 index로 일대일 대응. 기존 곡은 영상 모듈 하단의 「정렬 복구」버튼으로 한 번에 수정 가능."
  ⚠️ 이는 **AI가 스스로 서술한 완료 상태이며 독립적 검증 결과가 아니다.** 아카이브에는 그 이후 사용자가 "이제 정렬된다"고 확인한 회신 메시지가 **없다** — #1476은 곧바로 글자 크기 스타일로 넘어갔다. 따라서 엄밀히 말해 **"수정이 실제로 효과를 냈다"는 점은 아카이브 상 사용자 측 확인이 결여되어 있다.**
